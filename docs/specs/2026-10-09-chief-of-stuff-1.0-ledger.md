## How to read it

- **carry**: bring the code or behaviour across essentially as is (port the module and its tests).
- **rewrite**: keep the behaviour, build it again on the new model (issue-keyed store, engine, one model adapter, board items, exception pings).
- **drop**: do not bring it. The reason is stated.
- **unknown, needs owner**: I could not decide from the repo and the design. The lean, if any, is in brackets.
- **PRESERVE THE BEHAVIOUR** in the Why column marks a behaviour that fixed a real field incident. The behaviour must survive even where the code is dropped. Finding numbers (for example "finding 27") are entries in the original workspace's field notes, which are not published; the behaviour each one preserves is stated in its row. `#NNN` are issue numbers quoted in the code.
- Row IDs: A contract and docs, B agent file, C skills, D state and config, E engine and workers, F git/forge/review/merge, G messaging and notify, H board and pages, I eval harness and unit tests, V the 110 eval cases by family.

## What I found that the design does not say

1. **No worktree cleanup exists in the repo.** The design says stale worktrees used 185 GB once and that cleanup must be preserved. I found no code that removes worktrees, branches or build output. `make_worktree.py` states it never removes them, and the agent file forbids the coordinator from doing it, after finding 27 (five worktrees removed, gitignored plans and a database snapshot lost). So there is nothing to carry. Row E19 asks the owner where the cleanup lives. Any new cleanup must keep finding 27's guard.
2. **`evals/test_architecture.py` is not yet the circle-table enforcer.** `CLAUDE.md` and ARCHITECTURE.md section 5 describe it that way, but compliance row C1 records that it holds only page-module lists, import probes and a cycle check. Carrying it means building the circle table first.
3. **Section 9 (agent performance) is specified but not built** (C8). Row A3.
4. **Scale:** 60 scripts (16,145 lines), 71 test files (3,124 test methods by static count, including the 2,000+ that test modules this ledger rewrites), 110 eval cases of which 21 are golden. Churn hot spots named in the design: `audit_tasks.py`, `one_shot.py`, `dispatch_prompt.py`, `git_trees.py`. All four are rewrites here (F5, E4, E3, F2).
5. **The engine does not exist yet.** `flow.py` is a partial tick, run by a `UserPromptSubmit` hook. It does not merge, launch reviews, or resume after quota (E1).

2. carry: 25 rows (22 module/behaviour, 3 eval families) and 9 of the 110 eval cases.

7. Riskiest drop 2: terminal launchers (E9, E11). The launchers go, but their start verification (E10, #551) must be rebuilt or "said a launch succeeded when it failed" returns.
8. Former riskiest drop 3, kanban label sync (F11): no longer dropped. Stage is written back to GitHub Project Status or GitLab labels (F11 above, owner 2026-10-11).
9. Riskiest drop 4: the markdown tracker with no import (D1, D2, D12, V3, V6). Work in flight at cutover has no record unless the old harness runs beside the new one (M7).
10. Riskiest drop 5: the peer-session roster and interactive proposal flow (V20, V8, B14). If the owner still runs standing interactive sessions, the engine has no way to talk to them. Worktree cleanup (E19) is the riskiest gap, not a drop: nothing exists to carry.
