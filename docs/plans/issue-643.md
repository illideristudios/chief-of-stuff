## Resulting behavior and contracts

### M6.1: Store-backed board, gantt and pages

1. Add a narrow `scripts/board_query.py` use case with an injected read port. `board_sources.py` becomes the gateway adapting the approved repository to that port. Renderers receive plain immutable values, never ORM sessions/rows. Reuse upstream issue/segment/decision types and keys where available rather than defining a second canonical model. Proposed port operations are a workspace snapshot for a time window and lookup by canonical issue key; exact names follow M1.
2. One snapshot carries a committed revision, work items, stage segments, decisions, persisted worker/change/review facts and source freshness/errors. Read all related records in one short transaction, materialize them, and close it before rendering. The page request path performs no forge polling, git fetch, process reconciliation, model call or store mutation. Existing cached diff/graph enrichment stays optional, outside that transaction; missing enrichment shows unavailable detail rather than blocking the board. M3/M2 own refresh of facts, including any source details formerly fetched directly by `source_page.notes`.
3. Group by canonical issue key before constructing board cards and gantt rows. A stage segment is identified by `(issue_key, stage, attempt)`; several workers, PRs, reviews or attempts never create additional issue rows. Sort deterministically by real start, stage and attempt. Preserve overlapping segments and rework; never combine or truncate them because another attempt finished. The current state/status comes from the work item, not whichever segment happened to sort last.
4. Feed `flow_chart.py` from segments, retaining `gantt.py` as a presentation leaf that receives rows. Preserve palette, layout, focus/tooltips and existing chart windows. Tooltips identify stage and attempt. Clip only presentation to the selected window. An open segment draws to the injected current time and is identified as running; an absent start/end is unknown, never an invented completion or deadline. Keep forecasts visually separate and exclude them from measured history. Issues with no segments still have one board item; the selected chart window determines chart inclusion explicitly, without generating synthetic history.
5. Switch issue, source and worker pages and all counts/panels to the same store projection. No dependency on today's tracker existing, old daily logs, decision JSON, `.sources.json`, or task-name matching in the M6 path. Archived trackers remain untouched. Extract shared public helpers into `scripts/page_kit.py` for §3/C4; keep legacy helper re-exports where callers still require them until M7.
6. Replace tracker/cache mtime freshness in the M6 server path with committed store revision plus renderer/config/theme version and selected window/day. Capture revision with the snapshot; a later commit must invalidate the next request even if filesystem timestamps match. A failed render retains last good HTML with a visible error; a fresh install with an empty store renders an empty board. Store unavailable is an explicit error, not an empty successful snapshot. Scope caches and revision state by workspace.

### M6.2: Full issue keys in routes and board decisions

1. Add `scripts/issue_routes.py`, a small presentation helper using the upstream canonical key parser and standard-library URL encoding. Proposed routes: `/issues/<encoded-full-key>` and `/issues/<encoded-full-key>/source`, with the full key percent-encoded as one component. The canonical identity must distinguish forge/host, repository/project and issue number, including nested GitLab groups. One encode/decode round trip, no trailing-number inference or default-backlog qualification. Validate with the upstream parser; reject malformed, double-encoded and unknown identities. Generated filenames use an opaque safe digest of the full key and view, never raw route text as a filesystem path.
2. Update board cards, gantt rows, panels, workers, issue/source cross-links and ping URLs together. Bare-number routes may redirect only when the store proves one unambiguous canonical match; otherwise return 404/conflict without selecting an arbitrary repository. Keep direct generated HTML/dotfiles inaccessible and preserve loopback, Host/Origin checks and request size limits.
3. Render pending human decisions as board items with stable persisted decision IDs, context, linked issues, options, recommendation, trio verdict/reason and answer controls. Use a stable `/#decision-<safe-id>` anchor for deep links. Automatic unanimous decisions appear as resolved/audit items and do not request an answer. Global limit/failure decisions need no invented issue: decisions have their own identity and never become extra issue gantt lines.
4. Use a board action such as `POST /board/decisions/<encoded-id>/answer`, calling M5's answer use case with decision ID, expected revision, selected option and/or the user's words. Validate eligibility and input server-side. Commit once, preserve attribution/time and verbatim answer, then redirect to the board anchor. Repeated identical submission is idempotent; a stale or different second answer returns conflict and does not overwrite the accepted answer. Only the engine resumes affected work on its next reconcile; the HTTP handler does not dispatch or merge.
5. Stop generating standalone decision JSON/HTML in the M6 path. Redirect existing decision routes to board anchors only when a persisted legacy-ID mapping exists; absent a mapping, return a clear retired/unknown response. Do not import old JSON decisions or guess identity from a slug. Remove separate decision navigation in the new board; pending counts and answered state come from the same committed snapshot. Keep archival artifacts and defer general legacy removal to M7.

### M6.3: Exception-only pings

1. Add `scripts/notification_policy.py` as a pure use case over M5's persisted eligible exceptions: unresolved goal ambiguity after the trio, unrecoverable failure after retries, and approaching configured spend/quota/time limits. The engine's verdicts and thresholds are authoritative; notify must not run another trio, infer eligibility from prose, or invent limits.
2. Routine progress, merge readiness, a unanimous trio outcome, retryable outages/quota waits within policy, successful completion, quiet ticks, ordinary deadlines and day reminders produce no ping. The pending owner scope conversation must settle the routine reminder retirement before implementation. The legacy notification service must no longer start an independent flow tick in the M6 engine path.
3. Adapt the existing notifier/queue with stable persisted exception IDs rather than clock-based titles. A ping contains concise context and a board-item URL in its message. Preserve the empty Open field: link to the board without automatically opening a browser. Respect the disabled adapter and preserve unrelated queue rows, parked acknowledgments, lock discipline and atomic replacement.
4. Use M5's durable delivery/outbox state. Render/create the board item before attempting delivery. Retry transport failure without losing the exception or changing its ID. Deduplicate at the adapter by that stable ID as well as recording delivery in the store, covering a crash after queue insertion but before acknowledgment. Claim concurrency through the repository, not a process-local set. Do not claim cross-system exactly-once delivery; the target is one queue event under retries via idempotent insertion. A newly reopened exception has a new persisted occurrence ID; the same pending occurrence is not repinged on restart or midnight.
5. M3 owns the scheduler/supervisor. Keep notification adapter compatibility as needed, but replace tracker-based fingerprints with store revision/exception state. A failed notification is recorded as delivery failure for the engine's retry policy, not recursively notified by the adapter.
